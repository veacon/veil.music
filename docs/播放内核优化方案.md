# Veil Music 播放内核优化方案（对标开源实现）

> 目标：在**不换引擎**的前提下，把解码格式覆盖、设备兼容、卡顿与资源占用做到这批开源播放器里靠前的水准。
> 结论先行：真正卡我们的不是「缺功能」，而是**几处配置和一处打包缺陷**；先修这些，收益远大于换引擎。

**两处对原方案的修正**

1. **FFmpeg 缺失不会崩**：`FfmpegLibrary.isAvailable()` 自己 catch 了 `UnsatisfiedLinkError`，只是渲染器静默不可用。所以 64 位设备的表现是「某些格式放不出来」，不是闪退。现在启动日志会打 `ffmpeg=missing abi=...`，设置页也能看到。
2. **电台不是「已取消」而是「页面没了、链路还在」**：`RadioScreen` 有路由但无人导航；真正还能触发 `buildRadioExoPlayer` 的是浏览/首页的 `ra.` 卡片。现已整条删除。

## 0. 结论摘要

| 优先级 | 事项 | 工作量 | 预期收益 |
|---|---|---|---|
| **P0-1** | 缓冲按「纯音频」重新定标：180s / 32MB → 60s / 8MB + back buffer 15s | 0.5 天 | PSS 降 20–25MB，OOM 风险从「随时」降到「基本不会」 |

| **P1-1** | 解码器策略模块（硬解白名单 + FFmpeg 兜底 + 设备黑名单） | 2 天 | 硬解命中率与失败率都可控，出问题能定点屏蔽 |
| **P1-2** | **FFmpeg 扩展补 arm64-v8a**（现在只有 armeabi-v7a） | 1–2 天 | 64 位设备上软解不再缺失；这是当前最大的兼容缺口 |

不建议做：把 libmpv / libVLC 作为第二引擎塞进来（详见第 7 节）。

## 1. 现状体检（本仓库实测）

| 项 | 现状 | 备注 |
|---|---|---|
| 引擎 | `androidx.media3:media3-exoplayer:1.4.1` | 当前稳定线 **1.11.1**，跨 7 个小版本 |
| 播放器实例 | ~~3 套~~ → **2 套**：主播放器、交叉淡入播放器 | 电台那套已整条移除；两套共用 `PlaybackTuning` |
| 解码 | MediaCodec + 自建 FFmpeg 扩展（`app/libs/media3-ffmpeg.jar` + `jniLibs`） | FFmpeg 只编了**一个 ABI** |
| 输出 | `DefaultAudioSink` + 3 级 `AudioProcessor`（GapConceal → Gain → Beat） | 没有自定义 AudioTrack 缓冲 |
| 缓冲 | `DefaultLoadControl`：min 50s / max 180s / target **32MB** | 按视频/长流媒体定标，对 3–5 分钟的音频严重过量 |
| 缓存 | 播放链路**没有** `CacheDataSource` | 同一首歌重播仍走网络 |
| 解码选择 | 只有「软解模式下 AAC 优先 OMX.google」一条特例 | 没有设备级策略、没有能力探测 |
| 稳定性 | 只有「切解码方式时重建播放器」一条自愈路径 | 没有 underrun/卡死检测 |
| 实测设备 | XGIMI TV，SoC `arm64-v8a`，`primaryCpuAbi=armeabi-v7a`，Android 8，2GB RAM | 应用实际以 **32 位** 运行 |
| 实测内存 | PSS 94MB（Native 30MB / Dalvik 22MB / dex+apk mmap 21MB） | 曾因 50MB 堆上限 OOM 两次 |

### 1.1 已经确认的两个硬缺陷

**(a) FFmpeg 扩展只有 32 位**

```
app/app/src/main/jniLibs/armeabi-v7a/libffmpegJNI.so   ← 只有这一个目录
```

这台电视的 SoC 是 arm64，但因为它的 `abilist` 把 `armeabi-v7a` 排在前面，应用被装成 32 位，所以软解还能用 —— **纯属运气**。换一台只接受 64 位的盒子（或走 Google Play 的 64 位强制要求），`EXTENSION_RENDERER_MODE_PREFER` 下 FFmpeg 渲染器加载失败，软解模式直接不可用。

我用字符串扫描确认了这个 `.so` 里带着 `flac / alac / ape / wavpack / opus / vorbis / mp3 / aac / ac3 / eac3 / truehd / dts` 的解码器名，也就是说**构建脚本本身是多格式的，只是没编 64 位**。补 ABI 是纯工程活，不是重写。

**(b) 缓冲参数与「音频」场景不匹配**

- `targetBufferBytes = 32MB` 是按 320kbps 流「攒够时长」倒推的，但在 2GB RAM / 50MB 堆的盒子上，这 32MB 全是 Java/Native 堆外压力；之前那两次 OOM（语义树遍历、SharedPreferences 写盘）本质就是内存水位太高。
- `maxBufferMs = 180s` 对 3 分钟的歌等于「整首预载」，收益只有首播抗抖动，代价是切歌时释放大量缓冲。

## 2. 可借鉴的开源项目

> 「可复用」列区分了三种方式：**直接用**（依赖/配置）、**抄结构**（照它的设计在本仓库重写）、**只借思想**（不引入代码）。

| 项目 | 许可（以仓库 LICENSE 为准） | 它怎么做的 | 我们能复用什么 | 方式 |
|---|---|---|---|---|
| **androidx/media3（ExoPlayer）** | Apache-2.0 | 官方音频管线；`DefaultAudioSink` 提供 `setAudioTrackBufferSizeProvider` / `setOffloadMode`；`DefaultLoadControl` 提供 back buffer 与 allocator；`MediaCodecSelector` 允许接管解码器挑选 | 全套：缓冲定标、offload、解码器策略、`setEnableDecoderFallback` | **直接用** |
| **VLC / libVLC** | LGPL-2.1+ | 音频输出是一串**按能力排序的模块**：AAudio(190) > AudioTrack(180) > OpenSL ES；AudioTrack 内部还有 `stereo → pcm → encoded` 的声道/格式回退；缓冲上限 750ms | 「输出后端按能力排序 + 失败逐级回退」的骨架；AudioTrack 参数回退顺序 | **抄结构** |
| **mpv / libmpv** | GPLv2+（可编成 LGPL 的 libmpv） | `--gapless-audio=weak`：音频设备常开，格式变化才重开；`--audio-buffer` 默认 200ms；AAudio 输出可 `--audio-exclusive`；重采样用 soxr；变速走 scaletempo2 | 「设备常驻 + 格式统一」的思路；缓冲时长语义（200ms 量级，而不是秒级预载）；`audio-fallback-to-null` 式降级 | **只借思想** |
| **Auxio** | GPL-3.0 | 纯 Media3 的音乐播放器，`AudioProcessor` 链做 ReplayGain，输出设备变化时重建 sink，Service 生命周期极简 | 输出设备切换（HDMI/蓝牙）时的 sink 重建时机；ReplayGain 处理器写法 | **抄结构** |
| **RetroMusic / Metro** | GPL-3.0 | ExoPlayer + 均衡器/音效链、播放队列持久化 | 音效链挂载位置；队列/书签持久化边界 | **抄结构** |
| **Oboe** | Apache-2.0 | AAudio/OpenSL ES 的统一封装，含格式协商与失败回退 | 若将来自研 sink，照它的格式协商顺序；现在**不需要**引入 | **只借思想** |
| **FFmpeg** | LGPL-2.1+ | 解码器 + `aresample`（可接 libsoxr） | 多格式解码（已有）、高质量重采样 | **直接用** |
| **libsoxr** | LGPL-2.1 | 高质量重采样内核 | 仅在 P2「统一输出格式」需要时接入 | **可选用** |

## 3. 优化范围（按层拆）

### L1 解码层

| 改动 | 具体做法 | 落点 |
|---|---|---|
| 解码器策略模块 | 把 `audioCodecSelector` 抽成 `DecoderPolicy`：① 优先硬解（`MediaCodecInfo.isHardwareAccelerated()`，API<29 用名字启发式排除 `google`/`c2.android`/`software`）；② 按格式给白名单（FLAC/ALAC 优先硬解，APE/WavPack 直接走 FFmpeg）；③ 设备级黑名单（`Build.MODEL`+codec 命中即跳过）；④ 连续失败 N 次自动降级并落盘 | `media/DecoderPolicy.kt`（新增）+ `PlayerViewModel` |
| 启动能力探测 | 首次启动后台用 0.3s 静音样本试解各格式，结果缓存到 prefs，避免「播到第 3 首才发现这个格式不行」 | `media/DecoderProbe.kt`（新增） |
| FFmpeg 补 ABI | 重建 `libffmpegJNI.so`：`arm64-v8a` + `armeabi-v7a`（+ 模拟器 `x86_64`）；保留现有解码器集合 | `app/src/main/jniLibs/**`、构建脚本 |
| 回退链显式化 | 软解模式下：FFmpeg 优先 → MediaCodec 兜底；硬解模式反过来。现在只靠 `EXTENSION_RENDERER_MODE_PREFER/OFF` 两档，缺「单格式级」回退 | `PlayerViewModel.buildExoPlayer` |

### L2 输出层

| 改动 | 具体做法 | 落点 |
|---|---|---|
| AudioTrack 缓冲定制 | `DefaultAudioTrackBufferSizeProvider.Builder().setTargetPcmBufferDurationUs(600_000)`（VLC 上限 750ms、mpv 默认 200ms，取中间值），TV 上抗瞬时抖动 | `BeatAwareRenderersFactory` |
| 统一输出格式 | 按 `AudioManager` 报告的设备采样率（TV 多为 48kHz）统一输出，避免 44.1k/48k 来回切设备导致 sink 重建与爆音 | 同上 + `AudioProcessor` 前置重采样 |
| 输出参数回退 | 照 VLC 的顺序：目标格式失败 → 降 16bit → 降 stereo。目前 `setEnableFloatOutput` 由系统决定，失败后无退路 | `BeatAwareRenderersFactory` |
| 设备变化监听 | HDMI/蓝牙切换（`AudioDeviceCallback`）时主动重建 sink，而不是等 underrun | 新增 `AudioRouteMonitor` |
| 音频 offload（P2） | 当 Gain/Beat 处理器关闭时 `sink.setOffloadMode(ON)`：解码交给 DSP，CPU 与功耗双降 | `BeatAwareRenderersFactory` + 设置项 |

### L3 缓冲与网络

| 改动 | 具体做法 | 落点 |
|---|---|---|
| 缓冲重新定标 | `setBufferDurationsMs(20_000, 60_000, 1_500, 3_000)`；`setTargetBufferBytes(8MB)`；`setBackBuffer(15_000, false)`；`setAllocator(DefaultAllocator(true, 64*1024))` | `PlayerViewModel.buildExoPlayer` + 另外两个播放器 |
| 磁盘缓存 | `SimpleCache` + `CacheDataSource.Factory`（复用现有 `DiskBudgetStore` 的预算），命中即秒开、离线可播 | `data/cache/` + MediaSource 构建 |
| 统一 datasource | 主播放器现在用 `DefaultHttpDataSource`，音乐视频已用 `OkHttpDataSource`。统一到 OkHttp：连接池复用、HTTP/2、可观测 | 同上 |
| 预解析与预取解耦 | 现有 `prefetchSong` 只预热歌词与落雪直链，不预载音频字节；配合磁盘缓存做「下一首前 10% 预取」 | `PlayerViewModel.prefetchSong` |

### L4 稳定性与自愈

| 改动 | 具体做法 |
|---|---|
| 卡死看门狗 | 播放中每 2s 采样 `currentPosition`；连续 3 次不前进 → 记 `WDOG` → 重建 sink；再失败 → 换解码器重试；仍失败 → 跳下一首 |
| 错误分级 | `PlaybackException` 按 `errorCode` 分类：网络类重试 3 次（指数退避）、解码类切解码器、DRM 类直接跳过 |
| 单例播放器重建收敛 | 现在 3 处 `buildExoPlayer()` 调用各自复制配置，收敛成 `PlayerFactory.build(config)`，避免改一处漏两处 |
| 崩溃可观测 | 已有 `CrashReporter` 落盘；补一条「最近 200 条播放事件环形缓冲」写入崩溃日志，便于事后归因 |

### L5 资源占用

| 改动 | 具体做法 |
|---|---|
| 图片缓存按设备定标 | Coil 现在固定 64MB；`ActivityManager.isLowRamDevice`/`memoryClass<96` 时降到 24MB |
| 原生内存审计 | 实测 Native 30MB 偏高（QuickJS 脚本 + Coil + 解码缓冲）；给每个脚本引擎设内存上限，异常脚本卸载 |
| 播放线程优先级 | `ExoPlayer.Builder.setPlaybackLooper` 用独立 HandlerThread，`Process.setThreadPriority(THREAD_PRIORITY_AUDIO)` |

## 4. 分批落地

### P0（1–2 天，低风险，先摘果子）

1. **缓冲定标**（L3）：改 3 处 `LoadControl`，加 `backBuffer`。
2. **AudioTrack 缓冲**（L2）：一个 Builder 调用。
3. **看门狗 + 错误分级**（L4）：新增 ~120 行，不改现有结构。

验收：连续播放 2 小时不 OOM；`dumpsys meminfo` PSS 下降；人为断网 10s 后能自愈。

### P1（3–5 天，需要改打包与策略）

4. **DecoderPolicy + 能力探测**（L1）。
5. **FFmpeg 补 arm64**（L1）—— 需要 NDK 构建环境，建议写进 `tools/build-ffmpeg.sh` 固化。
6. **统一输出格式 + 磁盘缓存**（L2/L3）。

验收：64 位设备上软解可播 FLAC/APE；同一首歌二次播放 0 网络请求；硬解命中率日志可统计。

### P2（1–2 周，收益长期）

7. **升级 media3 1.4.1 → 1.11.x**：新版音频渲染器对瞬时 underrun 加了宽限期（不再误判为 buffering）、PCM 缓冲默认值改为固定 500ms，还有 Matroska ALAC、MP3 gapless 元数据修正等（见 androidx/media#3210）。代价是 `AudioSink.configure` 签名变更、`UnstableApi` 迁移。
8. **音频 offload**（L2）。
9. **高质量重采样**（L2，可选 libsoxr）。
10. **gapless 深化**：现有「同专辑预加载下一首」扩展为跨专辑 + 精确样本级衔接。

## 5. 可行性评估

| 项 | 依赖 | 风险 | 结论 |
|---|---|---|---|
| 缓冲定标 | 无 | 网络极差时首播等待变长（可用 20s min 缓冲兜住） | **高可行**，建议立刻做 |
| AudioTrack 缓冲 | 无 | 过大会让 seek/暂停响应变钝（600ms 在可接受范围） | **高可行** |
| 看门狗 | 无 | 误判（长时间缓冲时位置也不动）→ 需排除 `STATE_BUFFERING` | **高可行**，注意条件 |
| DecoderPolicy | `MediaCodecUtil`（已用） | 白名单需要真机验证，先给保守默认 | **中高**，分两步走 |
| FFmpeg 补 arm64 | NDK + ffmpeg 源码 | 构建脚本丢失（仓库里只有产物，没有脚本）→ 需要先复原构建参数 | **中**，工作量主要在环境 |
| 磁盘缓存 | 无 | 需要处理「代理 URL 每次不同」的 cacheKey 归一化 | **中高** |
| 升级 media3 | — | API 破坏性变更、三套播放器同时迁移、需重跑实机矩阵 | **中**，建议单独立项 |
| 音频 offload | 需关闭处理器链 | 与 Gain/Beat 互斥；部分 TV 固件 offload 有 bug | **中低**，做成可选开关 |

## 7. 明确不做

| 方案 | 为什么不做 |
|---|---|
| 引入 libmpv/libVLC 作为第二引擎 | APK +8–15MB；双栈维护；字幕/进度/MediaSession 全要重接；我们现在缺的只是配置与一个 ABI，不是能力 |
| 自研 Oboe AudioSink | 会丢掉 Media3 的处理器链（GapConceal/Gain/Beat）与无缝衔接；AAudio 的收益主要在低延迟交互，音乐播放用不上 |
| DSD 原生直通 | 目标设备不具备对应 DAC 通路，且源站基本不提供 |
| 为每种格式写独立播放器 | 与「统一管线 + 策略选择」相悖，维护成本爆炸 |

## 8. 附：本次体检用到的事实出处

- media3 版本与最新稳定：`dl.google.com/dl/android/maven2/androidx/media3/media3-exoplayer/maven-metadata.xml`（最新稳定 1.11.1）

- 设备以 32 位运行：`dumpsys package com.veacon.veilmusic | grep primaryCpuAbi` → `armeabi-v7a`
