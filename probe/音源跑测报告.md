## 2. 跑测机制（新增 `LxBench`）

不能靠「脚本能不能加载」判断可用性：44 条里有 40 条都能正常 `init` 并声明 wy/tx/kg，但后端早已失效。

跑测对每条脚本走**真实链路**：

1. `PlatformSearch` 搜网易云/QQ/酷狗 → `TrackMatcher` 打分 → 每平台取最高分候选（拿到平台 ID）
2. 对该脚本声明的每个音源调用 `musicUrl(source, 320k, musicInfo)`，单次上限 10s
3. 拿到的直链交给 `StreamVerifier` 做真实字节校验（读首段，判定 flac/mp3 + 反推码率）
4. 输出 CSV：`file,source,ok,ms,kind,kbps,track,detail`

入口：`am start -n <pkg>/com.applemusicktv.luoxue.LxPocActivity --ez bench true [--es tracks '歌|歌手|专辑|秒;…']`

## 7. 已知问题

- **tx（QQ 音乐）码率普遍偏低**：多次出现 28–38kbps，判断为试听片段。当前由 `StreamVerifier` 的 `kbps >= 200` 门槛挡掉，等于 tx 实际可用率很低，主力覆盖靠 wy/kg。
- **部分脚本 resolve 后仍留定时器**：quickjs-kt 的 `evaluate` 要等所有异步作业结束才返回，这类脚本会一路等到超时（洛雪音源14.js、杰翔）。已在 `musicUrl` 超时后调用 `interruptEvaluation()`，避免拖累后一档。
- **首曲偏慢**：第一次解析包含 4 个 QuickJS 实例初始化（约 1.5–2s），后续曲目靠预取可掩盖。
