# P0 探针实测报告：Apple 元数据 → 落雪音源

> 测试时间：2026-11-06 16:20–16:35（GMT+8）
> 测试机：本机（Windows，直连网络，无代理）
> 样本：Apple 目录（US storefront，未登录，仅抓取 bearer）真实曲目 20 首
> 脚本：用户提供的 `洛雪音源.zip` 全部 15 个脚本
> 校验：解析出的直链实际下载 64 KB，按魔数判定容器（`fLaC`/`ID3`/`ftyp`），用 `Content-Range` 总长 ÷ 时长反算真实码率

---

## 一、结论（三句话）

1. **"落雪音源不能按歌名直接播"是真的，但可以绕开。** 15 个脚本里只有 1 个（K×H）接受"歌名+歌手"并返回 URL，而且它返回的是 **128 kbps MP3**，请求 `master` 也一样——高音质请求被静默降级。
2. **自己补一层搜索、把平台曲目 ID 注入 `musicInfo`，局面完全反转**：7 个脚本能产出真 FLAC，实测最高 **3534 kbps**；完整链路 20 首 **19 首成功（95%），其中 18 首是真 FLAC（90%）**。
3. **端内（无 PC）完全可行**：整条链路只有"搜索 HTTP + JS 执行 + 直链播放"，不依赖任何服务端；峰值耗时 p50 239 ms，但**尾部很长（最坏 40 s）**，必须靠超时 + 早降级兜住。

```

  → 20 首样本(含 华语/欧美/摇滚/独立/古典/现场/OST/说唱/日语)
```

| 实验 | 变量 | 目的 |

## 四、暴露出四个必须解决的问题（这是 P0 最有价值的产出）

### 1. 繁简 + 跨语言标题导致误判（唯一 MISS 的原因）

Apple 侧：`後來的我們` / `Mayday`；平台侧：`后来的我们` / `五月天`。
标题二元组重叠为 0、艺人不匹配，总分只有 20，被阈值挡掉——**但平台上确实有这首歌（wy 422104138，346s，专辑《自传》）**。

同理 `Wayfarer`（Apple 用英文曲名）对应平台的 `山海`，标题匹配直接失效，最后靠时长+艺人兜到。

**修复**：
- 用 Android 自带 `android.icu.text.Transliterator("Traditional-Simplified")` 做繁转简（API 24+，minSdk 23 需兜底）；
- 艺人别名表（Mayday↔五月天、G.E.M.↔邓紫棋、Jay Chou↔周杰伦…）先做 Top 200，后续可从匹配失败样本里长出来；
- **标题匹配失败时走第二遍策略：只按艺人搜索 + 时长 ±3s 过滤**（实测能把 `山海 251s` 精确捞出）。

### 2. 版本错配（能播但不是那首歌）

`Into The Night`（Apple 是 2024 东京巨蛋 Live，293s）匹配到录音室版 262s；`Blinding Lights (Remix)` 匹配到 Remix——后者正确，前者是"错版本"。
**修复**：版本词表（live/remix/instrumental/piano/acoustic/DJ/cover）双向比对，目标含 live 而候选不含 → 重罚；时长差 >15s 且有更好候选 → 换候选。

### 3. 直链有效期短（必须在架构里当一等公民）

实测网易云直链形如 `http://m8.music.126.net/20261106165542/.../xxx.flac`，路径里的时间戳 `16:55:42` 距解析时刻约 **21 分钟**；QQ 直链带 `vkey=`，同样是短时效。

**影响**：暂停超过 20 分钟再续播、或单曲循环很久后 seek，都会 403。
**修复**：ExoPlayer `onPlayerError` → 重新解析一次并保持进度；把"解析结果"当缓存而不是当 URL 存。

### 4. 尾部延迟与"假成功"

- 最坏样本端到端 40 s：因为按 `master → flac24bit → flac` 逐级试，每级失败都要等超时。
- `Content-Type` 不可信：FLAC 文件返回 `audio/mpeg`，必须靠扩展名/魔数决定 MIME，否则 ExoPlayer 可能选错提取器。

**修复**：单次解析硬超时 8 s、每首最多 2 个候选源、第一个 `flac` 成功即停（不再追 master）；`MediaItem` 显式设置 `mimeType`（按 `.flac` / 魔数）。

## 五、架构决策（由数据反推，已定）

```
┌─ 端内（无 PC）──────────────────────────────────────────────┐
│ 1. MetadataService   Apple 目录（bearer，未登录公开数据）    │
│ 2. SearchLayer       163 / QQ / 酷狗 三路搜索（Kotlin 直连）  │
│ 3. Matcher           繁简转换 + 艺人别名 + 时长兜底 + 打分    │
│ 4. ScriptHost        QuickJS 跑落雪脚本（lx.request/utils）   │
│ 5. Cascade           按源选脚本优先级，失败换脚本/换源        │
│ 6. Verifier          64KB 探测：真容器 + 真码率 + MIME        │
│ 7. Player            ExoPlayer + OkHttpDataSource             │
└──────────────────────────────────────────────────────────────┘
```

三条硬规则（P0 数据直接支撑）：

1. **搜索层必须自建**：不能依赖脚本内部的关键词兜底，否则只有 128k。
2. **脚本必须多路级联**：单脚本今天可用不代表明天可用（15 个里 6 个已死，就是证据）。
3. **解析结果必须校验**：不校验就会出现"看着成功、实际 128k"的假象。

## 六、Android 端落地要点（下一步）

| 项 | 方案 | 备注 |
|---|---|---|
| JS 引擎 | QuickJS（NDK，`arm64-v8a` + `armeabi-v7a`） | 脚本用了 async/await、可选链，Rhino/Duktape 不行 |
| `lx` 桥 | Kotlin 实现 `request/on/send/utils.buffer/utils.crypto`，JS 单线程 + 回调投递 | `request` 用的 OkHttp，需把结果切回 JS 线程 |
| 搜索 | OkHttp 直连 163/QQ/酷狗；酷我暂缺（反爬需 csrf） | 三个接口均已实测可用、无需登录 |
| 匹配 | ICU 繁简 + 别名表 + 时长兜底，映射结果落 Room | 一次匹配成功即缓存，避免重复搜索 |
| 播放 | `streamUrl(): String` → `resolve(song): AudioStream?`（suspend） | 影响 `playQueueItem`/跨淡/预取/`restoreState` 6 处 |
| 失效恢复 | `onPlayerError` → 重解析一次 + 保持 position | URL TTL ≈ 20 分钟 |
| 诊断 | Dev 页显示：命中率、平均解析耗时、当前脚本/源/真实码率 | 音源天天变，没有诊断页没法维护 |

## 八、遗留与风险

| 项 | 状态 |
|---|---|
| 酷我(kw)/咪咕(mg) 覆盖 | 未验证：酷我搜索接口需要 csrf/cookie；咪咕无公开搜索。当前可用源为 wy/tx/kg 三路 |
| 脚本长期可用性 | 6/15 已失效；依赖第三方付费/公共 API，**必须支持脚本热更新**（在线导入 URL + 版本号） |
| 母带/atmos | `master` 在 wy 上稳定返回 24bit FLAC（实测 5193–5469 kbps）；atmos 未测（需专用解码） |
| 版权 | 自用场景，按你的决定不处理；但脚本不内置进 APK、改为运行时可导入，可降低后续分发的成本 |
| 歌词 | 仍用 Apple 歌词；跨母带版本可能有 0.2–2 s 前奏差，需沿用现有 `LyricsOffsetPreferences` 并加自动对齐 |
